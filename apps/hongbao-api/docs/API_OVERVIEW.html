2. Bootstrap & request pipeline

  • CORS: allows http(s)://localhost:3000 and https://hongbao-chinese.vercel.app, with credentials.
  • Raw body on /api/clerk-webhook, so the Svix signature can be checked against the exact bytes.
  • Global pipe: ZodValidationPipe. Global interceptor: ZodSerializerInterceptor.
  • Global guards, in order: AuthGuard → CustomThrottlerGuard → RolesGuard.
sequenceDiagram
  autonumber
  participant C as Client
  participant AG as AuthGuard
  participant TG as ThrottlerGuard
  participant RG as RolesGuard
  participant V as ZodValidationPipe
  participant H as Controller → Service
  C->>AG: HTTP request
  alt route marked @Public()
    AG-->>TG: pass (no req.user)
  else
    AG->>AG: Bearer token → Clerk verifyToken
    AG->>AG: load User by clerkId (sub)
    AG-->>TG: req.user = User (or 401)
  end
  TG->>TG: key = user-id or ip · 3/1s · 20/10s · 100/60s
  TG-->>RG: pass (or 429)
  RG->>RG: check @Roles against req.user.role
  RG-->>V: pass (or 403)
  V->>H: validated DTO (or 400)
  H-->>C: { success, message, data, statusCode }

APP_GUARD providers are registered while NestFactory.create() runs. app.useGlobalGuards(RolesGuard) is called later in main.ts, so RolesGuard runs last and can read req.user.

6. Core business flows

6.1 Purchase → approval → access (payment checked by hand)

Students pay outside the platform (bank or wallet transfer) and send in a 6-character transaction reference. An admin checks the payment and approves it, and only then is access granted.

sequenceDiagram
  autonumber
  actor S as Student
  participant CP as ClientPurchaseService
  participant DB as PostgreSQL
  actor A as Admin
  participant PS as PurchasesService
  participant N as Notifications → FCM
  S->>CP: POST /purchase {items, paymentType, transactionNo, totalAmount}
  loop each item
    CP->>DB: find PUBLISHED course / mock test (404 if missing)
    CP->>CP: snapshot name, price, durationDays = perTime × 30
  end
  CP->>DB: TX: Purchase(PENDING, orderNo) + Items + Enrollments(PENDING)
  CP-->>S: purchase
  A->>PS: GET pending-approved
  A->>PS: POST purchase-approve {purchaseId}
  PS->>DB: TX: PENDING → PAID (no-op if already done)
  PS->>DB: lock User row FOR UPDATE
  loop each item
    PS->>DB: grantAccess (expiry rules)
  end
  PS-->>A: purchase
  opt granted
    PS->>N: "Enrollment Approved" (best-effort)
  end

Expiry rules: grantAccess

Item is lifetimenull (lifetime)
Current access is already lifetimestays null; a timed purchase never shortens it
Current access is active with an end datecurrent end date + days × qty (time stacks)
No access, or it expired / is pendingnow + days × qty, and startedAt resets

Safety guarantees

Idempotent: only the PENDING → PAID step grants access, so double clicks and retries do nothing.

Concurrency: a row lock on the user stops two approvals from both extending the same old end date.

Access check: status = ACTIVE and (expiredAt is null or in the future). Nothing ever sets EXPIRED, so code must always check the date too.

6.3 Coupon redemption

POST /coupon/apply {code, courseId}. The code is trimmed and upper-cased by the schema. These checks run in one transaction:

  1. Course exists
    2. →
  2. Coupon exists
    3. →
  3. isActive
    4. →
  4. startsAt ≤ now
    5. →
  5. expiresAt ≥ now
    6. →
  6. course allowed (empty = all)
    7. →
  7. perUserLimit
    8. →
  8. usedCount++ only if under usageLimit
    9. →
  9. create CouponRedemption

The increment is a single conditional update, so the global limit can't be oversold when requests arrive at the same time. DELETE /coupon/apply removes the user's most recent redemption and decrements usedCount.

The redemption is not linked to the purchase. The client applies the discount itself when it sends totalAmount.

  • find-all-quiz-for-attach lists non-mock quizzes that aren't attached to a course, lesson or sub-lesson yet.
  • Attaching a quiz to a mock test sets isMockTest = true and detaching sets it back, so mock-test quizzes stay out of the regular quiz list.
  • Uploads only accept allowed MIME types. Keys look like images|pdfs|audios/YYYY/MM/<uuid>.<ext> and the URL is ${R2_PUBLIC_URL}/${key}.
  • Client catalog lists only show published items. course-detail/:id does not check this.

6.5 Learning progress

POST /video/:id/complete marks the video as completed for the user (one record per user and video). GET /video/completed returns the IDs of completed videos.

The progress enum also lists COURSE, LESSON, SUB_LESSON, QUIZ, QUESTION and FLASHCARD, but only VIDEO has endpoints so far.

6.6 Push notifications

The client registers its FCM token with save-noti-token. The token is saved and assigned to the current user.

sendToUser sends to every token the user has and returns {sent, failed, total}, or 404 if the user has no tokens.

It runs automatically after a purchase is approved, and manually through send-to-user (ADMIN).
